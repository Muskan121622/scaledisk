- **Postgres CPU** is 6–10× the API's at every level → the DB is computing while the API blocks.
- **Postgres connections** climb to the **~94–96 / 100 pool ceiling** exactly where throughput
  inverts (≥100 VUs) → requests queue waiting for a connection.
- **Redis hit ratio ~97–98%** and low CPU → the cache is healthy, not a factor.
- **Kafka LAG / outbox pending** stay modest and drain between levels → the async pipeline keeps up.
- **Locks = 0, deadlocks = 0** throughout → contention is raw scan/sort cost, not row locking.

## Bottleneck (one line)

**PostgreSQL**, driven by the ticket-list `WHERE TenantId=@t ORDER BY CreatedAt DESC LIMIT 20`
having **no `(TenantId, CreatedAt)` index** → ~400 ms / 37k-buffer / 50k-row scan per call (proved
by `EXPLAIN`), which pins connections until the 100-pool saturates near 100 VUs.

**Fix (→ 5E):** add `(TenantId, CreatedAt DESC)`. Probe showed the same query at **0.199 ms / 22
buffers / 20 rows** (~2000× faster). Index was created then dropped in one command; no schema
committed in 5D.
